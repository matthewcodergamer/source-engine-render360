# Phase 5 — Safari 27 single-thread low-memory fallback

Status: design/audit target only. Do not replace the threaded Phase 3/4 runtime until the Phase 4 growable-memory profile has been measured on-device.

## Goal

Provide a second iPhone runtime that removes the SharedArrayBuffer pthread pool and PROXY_TO_PTHREAD overhead when WebKit's multi-threaded Wasm memory cost is the limiting factor.

Two runtime targets should coexist:

- `Portal-iPhone-threaded`: Phase 3/4 architecture, Source pthreads, SharedArrayBuffer, direct browser-backed VPK access.
- `Portal-iPhone-low-memory`: one Wasm execution thread, no Emscripten pthread pool, Safari 27 JSPI-backed asynchronous browser I/O.

This is not a compiler-flag-only conversion. Source currently relies on pthread ownership, atomic waits and PROXY_TO_PTHREAD behavior in several browser-port paths. Those assumptions must be removed or replaced deliberately.

## Browser requirements

The low-memory target should feature-detect, not user-agent-detect:

- `WebAssembly.Suspending`
- `WebAssembly.promising`
- the Emscripten JSPI runtime generated by `-sJSPI`
- WebGL2
- File/Blob browser APIs needed by the retail VPK source

If JSPI is absent, the low-memory target must fail closed with a clear diagnostic instead of silently changing execution semantics.

## Architecture

### 1. One Wasm execution thread

Remove these flags from the low-memory target:

- `-sUSE_PTHREADS`
- `-sSHARED_MEMORY=1`
- `-sPTHREAD_POOL_SIZE`
- `-sPTHREAD_POOL_SIZE_STRICT`
- `-sPROXY_TO_PTHREAD`
- `-sOFFSCREENCANVASES_TO_PTHREAD`

Keep MAIN_MODULE/SIDE_MODULE initially so the experiment changes one major subsystem at a time. If modern Emscripten rejects JSPI + dynamic linking for this project, isolate that as a separate blocker rather than folding it into the threaded profile.

### 2. Replace blocking browser handoffs

The current Emscripten port can block a Wasm thread while JavaScript obtains map data. In a single-thread browser target there is no worker thread that can safely sit in an atomic wait while the main event loop performs asynchronous work.

Replace those waits with JSPI-capable async imports. The C/C++ call sites should remain synchronous-looking, while the generated Wasm stack suspends until the JavaScript Promise resolves.

Initial conversion target:

- map discovery / `downloadMap` bridge used from Source's map lookup path

Then audit all other browser-specific blocking points before enabling the profile.

### 3. Retail VPK I/O

WORKERFS depends on synchronous worker-side File/Blob reads and is therefore not the final filesystem for a main-thread single-thread build.

The low-memory target needs one of these implementations:

1. JSPI VPK bridge: Source requests open/read/seek operations through async JS imports backed by `File.slice().arrayBuffer()`.
2. A single dedicated non-pthread Web Worker that owns the Wasm instance and uses synchronous File APIs, while the page remains UI-only.
3. A future Emscripten filesystem backend that exposes suitable asynchronous File/Blob access without copying the complete retail install into MEMFS.

Option 1 is the Phase 5 reference design because it maps directly onto Safari 27 JSPI and does not require SharedArrayBuffer.

### 4. Current-map-only residency remains mandatory

Phase 5 must retain the Phase 3 residency policy:

`menu-only -> current-map-only -> no future-map prefetch`

Removing pthreads is not permission to rebuild the old cumulative map loader. Retail VPK data remains browser-backed, and Source should only materialize resources it actually requests for the current level.

## Implementation order

1. Add a compile-only `low-memory` build profile with pthread flags removed and JSPI enabled.
2. Build MAIN_MODULE/SIDE_MODULE successfully before changing filesystem behavior.
3. Add runtime JSPI capability diagnostics.
4. Convert the map/download blocking bridge from atomic wait to an async JSPI import.
5. Implement async retail VPK open/read/seek bridge.
6. Boot menu/background1.
7. Start `testchmb_a_00`.
8. Transition to the next chamber and verify old map resources are released.
9. Compare WebContent memory, Wasm heap, JIT/module cost and frame time against the Phase 4 threaded build on the same iPhone.

## Success gate

Do not call Phase 5 viable until all are true:

- no SharedArrayBuffer requirement
- no Emscripten pthread workers
- JSPI capability is detected at runtime
- Source MAIN_MODULE/SIDE_MODULE dynamic loading still works or has a separately documented replacement
- menu reaches a visible first frame
- chamber 00 loads from the user's retail data
- one real level transition succeeds
- memory use is materially lower than the Phase 4 threaded profile
- failures produce a latest-only diagnostic instead of hanging the browser

## Non-goals for the first Phase 5 build

- no future-map prefetch
- no attempt to preserve every desktop Source worker thread
- no silent fallback to the 221+ MiB packed MEMFS background chunk
- no merge into the baseline branch until measured on-device
